# 播放模式与诊断

本文说明三种播放模式的请求链路差异、流代理的断点续传机制、诊断日志字段，以及当前仍未解决的已知观察项。

## 三种播放模式

配置项 `emby.playback_mode`，三态互斥：

| 取值 | 媒体流路径 | 工具是否取流 | 适用场景 |
|------|-----------|-------------|---------|
| `disabled`（默认） | 回退通用反向代理，由 Emby 按原响应处理 | 否 | 兼容 / 排障基线 |
| `redirect` | 工具返回 302，客户端直连 115 CDN | 否（仅解析跳转） | 一播到底、希望零中转带宽 |
| `stream_proxy` | 工具向 115 取流再转发给播放端 | 是 | 需要暂停续播、自由拖动进度条 |

关键差异：`redirect` 下工具只在开头参与一次，之后的 Range / seek / 暂停恢复请求都由客户端直接发给 CDN，工具既无法观测也无法重试；`stream_proxy` 下工具全程在场，可以在上游断链或直链过期时换链续传。`redirect` 的跨域问题通过注入 crossOrigin 拦截脚本解决。

## 断点续传机制（仅 stream_proxy）

响应头产出后若上游连接中断，`stream()` 记住已交付的绝对字节偏移 `seg_next`，在同一响应内调用 `resume_segment()`：

1. 从 `request.state.strm_source_url`（本次请求首次解析时保存的 STRM 源地址）或各级缓存取回跳转地址；
2. 换链时给跳转地址追加 `refresh=1`，让 302 服务跳过缓存、重新向 115 签发直链；
3. 以 `Range: bytes=<seg_next>-` 请求新直链，只接受 206 且 `Content-Range` 起点精确等于 `seg_next` 的响应；
4. 续传成功则继续同一响应体，播放端无感；失败则结束响应体并记录日志。

缓存口径：`PLAYBACK_STRM_CACHE_TTL_SECONDS` 为 6 小时（覆盖单次播放会话），已解析直链缓存 90 秒，解析失败仅缓存 5 秒且保留 `resolved=False` 标志，302 模式在解析失败时回退通用反代而非下发无效地址。

网段门禁 `_is_private_source()` 只使用连接层 IP（`request.client.host`），不信任可伪造的 `X-Forwarded-For`。

## 诊断日志

日志级别 INFO，管理面板 `/admin/api/logs` 可读取。所有直链经 `utils.describe_media_url()` 脱敏：只输出域名、路径与 `t_left=<剩余秒数>`，query 中的签名参数不落盘；请求头经 `utils.describe_headers()` 只输出 `名字(长度)`，值不落盘。

| 关键字 | 触发时机 | 关键字段 |
|--------|---------|---------|
| `【302跳转服务】签发诊断` | 新签发 / 缓存命中 / 取链失败 | pickcode、直链摘要、ttl、UA 前 60 字、force_refresh |
| `302 直链下发诊断` | `redirect` 模式替换 PlaybackInfo 的 Path | item_id、直链摘要、UA、播放端请求头名列表 |
| `302 直链解析失败诊断` | 跳转地址解析失败 | item_id、源地址摘要、UA |
| `流代理外发请求头诊断` | 流代理每次向 CDN 发请求前 | item_id、attempt、直链摘要、`all=` / `sensitive=` 头名列表 |
| `流代理续传外发请求头诊断` | 续传发请求前 | item_id、next 偏移、头名列表 |
| `流代理拒绝诊断` | 上游 403/404/5xx | status、直链摘要、UA、refresh、响应体前 200 字 |
| `流代理续传拒绝诊断` | 续传被上游拒绝 | status、直链摘要、断点偏移 |

`sensitive=` 单独列出认证类与条件类头（cookie、authorization、x-emby-token、referer、if-range 等），为空表示发出的请求头已是最小集合。`t_left` 为负或很小表示下发的直链已过期或即将过期。

## 已知观察项：115 CDN 403

`stream_proxy` 模式在高请求密度下，上游可能返回 `{"message":"115 pmt 3-2","status":403,...}`。2026-11-10 实测结论：

- 与直链有效期无关（`t_left` 11–12 小时）、与 UA 无关（签发与请求一致）、与请求头无关（外发头仅 `range` + `user-agent`，`sensitive=` 全空）；每次强制重新签发拿到全新直链后仍被拒。
- 99/103 个 403 出现在「前 60 秒 ≥11 次取流请求」窗口，平均 22.9 次；同为流代理模式的 14 时段低密度下 0 个 403。
- 302 模式对照时段（约 63 分钟播放）工具侧 0 错误、35 次新签发全部成功，但该时段请求密度较低，且客户端直连 CDN 的响应不经过工具、日志不可观测，因此不能据此断定模式差异是原因。

当前决策：**按观察处理，不改动播放逻辑**。现有证据更支持「115 侧对单位时间取流/签发密度敏感」，且工具的 403 重试链（3 次重试 × 每次强制重新签发）可能自我放大密度。若后续需要处置，候选方向见 `TODO.md`「115 限频响应识别」条目。

## 排查顺序

1. 确认当前 `playback_mode`（`config.json` 或管理面板）；302 模式下工具侧日志不会记录客户端直连 CDN 的失败。
2. 找到 `流代理拒绝诊断` 或 `流代理续传拒绝诊断` 行，读取 body 与 `t_left`。
3. 对照紧邻的 `流代理外发请求头诊断`，确认 `sensitive=` 是否为空、头集合是否异常。
4. 观察 `签发诊断` 的 `force_refresh` 与 `t_left` 回弹，判断换链是否真的重新签发。
5. 若为 `115 pmt 3-2` 且上述均正常，按密度观察项处理，避免重试放大请求。
